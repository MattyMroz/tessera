# E2: układ paczki npm i repo w dojrzałych bibliotekach komponentów React

Stan na 2026-10-31. Researcher, tylko odczyt. Każda biblioteka sprawdzona na pełnym drzewie gałęzi domyślnej (`gh api repos/<repo>/git/trees/<branch>?recursive=1`, żadne drzewo nie było obcięte) i na `package.json` paczki. Raport uzupełnia `r4-package-repo.md` (repo, build, dystrybucja); tu chodzi o układ plików wewnątrz paczki i jego związek z `exports`.

Oznaczenia: **F** fakt ze źródła, **W** wniosek z kilku faktów, **R** rekomendacja, **?** niewiadoma.

## Odpowiedź w skrócie

1. Nie ma jednego standardu układu komponentu. Biblioteki dzielą się po połowie: folder na komponent (Base UI, Mantine, Ark UI, Chakra) i płasko (Radix Themes, React Aria Components, shadcn, Park UI). Folder wybierają te, których komponent składa się z wielu części i plików (Base UI `menu/` ma 118 plików, Ark `popover/` 37). Płasko układają te, których komponent to jeden plik TSX i ewentualnie jeden CSS.
2. Biblioteką najbliższą Tesserze jest **Radix Themes**: stylowana warstwa nad prymitywami, statyczny CSS, tokeny jako pliki CSS dzielone według dziedziny. Ma płaskie `src/components/<nazwa>.tsx` + `<nazwa>.css` i eksport `./components/*` → `dist/.../components/*.js`. To ten sam kształt, który Tessera chce mieć (eksport per ścieżka, CSS obok).
3. Konsensus: kebab-case w nazwach eksportów i folderów, ESM z `"type": "module"`, `sideEffects` ograniczone do CSS, `files` z samym buildem (plus to, co ma czytać konsument), README w paczce, testy jednostkowe obok kodu, testy kontraktu paczki i testy przeglądarkowe osobno, skrypty generujące w `scripts/` paczki, strona/playground jako osobna aplikacja workspace.
4. Plan E2 jest w większości zgodny z praktyką. Odbiega w jednym punkcie, który ma koszt: foldery `engines/<silnik>/` i `components/<nazwa>/`, w których w E2 leży po jednym pliku. **R:** układ płaski według Radix Themes (szczegóły i lista zmian w planie na końcu).

## Konsensus

Punkty, w których zgadza się co najmniej 6 z 8 bibliotek albo wszystkie, których dotyczy pytanie.

1. **kebab-case w adresach publicznych.** Folder albo plik, który staje się ścieżką importu, jest kebab: Base UI `@base-ui/react/toggle-group`, Ark i Chakra `./*` → `components/<kebab>/`, Radix Themes `components/dropdown-menu`, shadcn `./message-scroller`. Mantine (PascalCase) w ogóle nie eksportuje ścieżek per komponent. Pliki wewnątrz są kebab w 5 z 8 (Radix Themes, Ark, Chakra, shadcn, Park).
2. **Jeden eksport = jeden komponent albo moduł.** Wszystkie biblioteki z publiczną paczką oprócz Mantine dają ścieżkę per komponent (`./button`, `./components/*`, `./*`). Zbiorcze `.` mają wszystkie poza `@shadcn/react`.
3. **`sideEffects` wąskie:** `false` bez CSS (Base UI, Ark, Chakra, shadcn), `["*.css"]` z CSS (Radix Themes, Mantine, RAC). Nikt nie zostawia pola pustego.
4. **`files` = to, co czyta konsument:** `["dist"]` (Ark, Chakra, shadcn), negacja źródeł (RAC), `.npmignore` (Mantine, Base UI). Dodatki tylko gdy konsument ich potrzebuje: Base UI dokleja Markdown dokumentacji jako `docs/` paczki, Radix Themes dokleja pliki CSS i wtyczki postcss.
5. **README w katalogu paczki** (wszystkie publikowane). CHANGELOG w paczce w 4 z 6 (Radix Themes, Ark, Chakra, shadcn).
6. **Testy jednostkowe przy kodzie, testy kontraktu paczki i przeglądarki osobno.** Obok kodu: Base UI, Mantine, Ark (podfolder), shadcn. Osobny katalog dla poziomu paczki: Base UI `test/public-types`, `test/node-resolution`, `test/regressions`. Testy wizualne na aplikacji demonstracyjnej: Radix Themes `apps/playground/tests`, Base UI `test/regressions`.
7. **Strona i playground to osobne aplikacje workspace**, nie część paczki (wszystkie 8).
8. **Generatory w `scripts/` obok tego, co generują,** poza `src`: Radix Themes `packages/radix-ui-themes/scripts/`, Base UI `packages/react/scripts/`, Park UI `packages/preset/generate-colors.ts`, Mantine i Ark w korzeniowym `scripts/`.
9. **Tokeny dzielone według dziedziny** (kolor, odstęp, promień, cień, typografia, ruch), jeden plik na dziedzinę: Radix Themes `styles/tokens/*.css`, Chakra `theme/tokens/*.ts`, Park UI `theme/tokens/*.ts`. Skale kolorów w podkatalogu, jeden plik na skalę (Radix `tokens/colors/`, Park `theme/colors/`).

## Różnice i ich przyczyna

- **Folder czy płasko.** Folder mają biblioteki z wieloczęściowymi komponentami i plikami pomocniczymi przy każdym (Base UI: część = podfolder z `.tsx`, `.test.tsx`, `DataAttributes.ts`, kontekstem; Ark: części, anatomia, examples, tests, stories). Płasko układają biblioteki, w których komponent to cienka warstwa: Radix Themes (stylowany wrapper nad Radix Primitives, 110 plików TSX w jednym katalogu), shadcn i Park (rejestr, plik = jednostka kopiowania), RAC (części w jednym pliku `Menu.tsx`). **W:** wybór wynika z liczby plików na komponent, nie z mody.
- **PascalCase czy kebab.** PascalCase mają starsze biblioteki z konwencją „plik = nazwa komponentu” (Mantine, RAC, Base UI dziedziczy po MUI). Nowsze (Ark, Chakra v3, shadcn, Park) i Radix Themes są w kebab. Base UI łączy oba: folder kebab (bo jest ścieżką importu), plik PascalCase.
- **Gdzie wygląd.** Headless (Base UI, Ark, RAC) nie mają tokenów. Stylowane trzymają wygląd albo obok komponentu (Mantine CSS Modules, Radix Themes `button.css`), albo w osobnej warstwie przepisów (Chakra `theme/recipes/`, Park `preset/src/recipes/`, shadcn `styles/style-*.css` z klasami `cn-*`, komponent bez wartości). Tessera ma oba: przepisy jak Chakra/shadcn plus opcjonalny CSS układu obok komponentu jak Radix Themes.
- **Wspólne bazy stylu.** Radix Themes ma `components/_internal/base-{button,menu,card,dialog,checkbox,radio,tab-list}.css`, czyli style współdzielone przez kilka komponentów. Chakra ma `layer-styles.ts` i `text-styles.ts`. To najbliższy odpowiednik przepisów Tessery (`control`, `surface`, `row`, `indicator`, `focus`).
- **Jak paczka widzi źródła w workspace.** RAC: warunek `"source"` w `exports` (jak Tessera dziś). Chakra: warunek `"dev"`. Ark: `exports` wskazują `src`, a `clean-package` podmienia je przy publikacji. Base UI: `exports` na `src`, build przepisuje i publikuje z `build/`.
- **Testy przeglądarkowe.** Na aplikacji demonstracyjnej z Playwrightem (Radix Themes) albo w Vitest browser mode obok kodu (shadcn) albo w osobnym katalogu (RAC, Base UI). Tessera wybrała pierwszy wariant; to model Radix Themes.

### Co zmienia się względem planu E2 (rekomendacja)

**R1. Silniki płasko: `src/engines/<silnik>.css` zamiast `src/engines/<silnik>/<silnik>.css`.**
Powód: w E2 każdy folder silnika ma jeden plik, bo generator koloru przeszedł do `scripts/`. Folder z jednym plikiem nie ma uzasadnienia w żadnej z 8 bibliotek; Radix Themes trzyma tokeny płasko. Gdy silnik dostanie kiedyś wyprowadzenie w TS, leży obok jako `<silnik>.ts`, tak jak Radix Themes trzyma `button.props.tsx` obok `button.tsx`.
Koszt zmiany: zmiana ustalenia F1 w spec (decyzja właściciela); `checkFor` w `css-layers.ts` rozpoznaje silnik po nazwie pliku zamiast folderu (inaczej płaskie pliki wypadają spod strażnika, patrz niżej); `engines-structure.test.ts` sprawdza 9 plików zamiast 9 folderów; reguła wzrostu w `structure.md` („nowy silnik = nowy folder”) zmienia się na „nowy silnik = nowy plik `<silnik>.css`, opcjonalnie `<silnik>.ts` i test obok”; importy w `tessera.css` krótsze o jeden poziom.

**R2. Komponenty płasko: `src/components/<nazwa>.tsx` (+ `<nazwa>.css`) zamiast `src/components/<nazwa>/<nazwa>.tsx`.**
Powód: komponent Tessery to cienka warstwa nad Base UI bez własnego wyglądu, czyli dokładnie przypadek Radix Themes, shadcn i Park, które układają płasko. Folder przy jednym lub dwóch plikach dodaje poziom ścieżki i wymusza przy eksporcie albo `index.ts` w każdym folderze (Base UI, Ark, Chakra, Mantine), albo wzorzec `./components/*` → `dist/components/*/*.js`. Płaski układ daje eksport z jedną gwiazdką, identyczny jak w Radix Themes. Dokumentacja komponentu i tak leży w `packages/tessera/docs/<nazwa>.md`, a testy zachowania w `apps/docs/tests/`, więc folder komponentu nie miałby czego zbierać.
Warunek odwrotu: gdy komponent zacznie mieć kilka własnych plików (części, kontekst, testy), lepszy jest folder. Rozstrzygnąć regułą raz dla całego katalogu, nie per komponent, żeby ścieżki eksportu się nie rozjeżdżały.

**R3. README w `packages/tessera/`.** Mają go wszystkie publikowane paczki z próby; npm pokazuje README z katalogu paczki, nie z korzenia repo. Poza zakresem E2, jeśli paczka zostaje prywatna; konieczne przed pierwszą publikacją.

**R4. (poza E2, do rozważenia) `publint` + `@arethetypeswrong/cli` jako część kontraktu paczki,** jak `test:package` w Base UI. Mogą zastąpić część własnych testów w `test/package/`. Wymaga osobnej decyzji o zależnościach.

Bez zmian, bo zgodne z praktyką: `scripts/` w paczce, `docs/` w paczce, `lib/theme/` i `lib/indicator/` jako foldery (moduły z kilku plików), testy jednostkowe obok kodu, `test/guards` i `test/package` osobno, Playwright w `apps/docs`, `_lab/` w `app/`, `exports` z `source`, brak `.`, `sideEffects`, `files`.

## Konflikty z obecnymi ustaleniami i niewiadome

- **F (lokalnie)** R1 jest sprzeczne ze spec: `docs/specification.md:128` (F1) mówi „Każdy z dziewięciu silników ma folder o tym samym kształcie”. R1 wymaga więc decyzji właściciela, nie tylko zmiany `structure.md`.
- **F (lokalnie)** Strażnik warstw rozpoznaje silnik po folderze: `packages/tessera/test/guards/css-layers.ts:219` zwraca regułę silnika tylko dla `engines/<silnik>/<plik>.css` (`rest.length === 1 && isEngine(folder)`); dla innej ścieżki `checkFor` zwraca `undefined`. Po R1 bez zmiany tej funkcji plik `engines/color.css` **nie byłby sprawdzany wcale**. R1 musi więc iść razem ze zmianą `checkFor` (silnik = nazwa pliku bez rozszerzenia) i fixture strażnika.
- Spec nie ustala folderu na komponent (szukałem w `specification.md`; jest tylko w `structure.md` i planie E2). R2 to zmiana dokumentu struktury, nie ustalenia. `checkFor` dla `components` nie zależy od głębokości ścieżki, więc R2 nie wymaga zmiany strażnika.
- Dla Radix Themes i Park UI aktywność repo jest niższa (ostatnie commity 2026-04 i 2026-02); układ źródeł się nie zmienia, ale nie ma dowodu, że to „obecna” praktyka. Najnowsze aktywne repo z tej samej grupy (shadcn, 2026-10-31) układa komponenty płasko, co wspiera R2.
